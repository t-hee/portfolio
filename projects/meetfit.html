01 / Overview

여러 사람의 일정을
하나의 흐름으로

모임에 참여하는 사람들의 가능한 시간을 모으고, 참석 조건을 반영해 후보 일정을 추천하는 서비스입니다. 모임 생성·참여·승인, 가능 시간과 캘린더, 일정 추천과 알림을 연결했습니다.

2026년 3월부터 6월까지 학기 프로젝트로 진행한 뒤 개선과 테스트를 이어갔습니다. React Native·Expo·TypeScript 앱과 FastAPI·SQLAlchemy·PostgreSQL·Alembic 기반 백엔드를 단독으로 개발했습니다.

05 / Recommendation Logic

모임마다 다른 조건을 반영하는 추천

고정된 기준만으로는 모든 모임의 요구를 담기 어렵습니다. 모임별 조건을 사용자가 설정하고, 결정적 규칙·점수 기반 로직이 후보를 평가하도록 구성했습니다.

  1. 사용자 설정 →
  2. 후보 평가 →
  3. 순위 결과
최소 참석 인원
후보 일정에 필요한 최소 참석 인원을 설정합니다.
필수 참석자 · 하드/소프트 모드
하드 모드는 필수 참석 조건을 제약으로, 소프트 모드는 참여 여부를 점수 평가에 반영합니다.
참석 불가 시간 처리
참석 불가 시간을 추천 평가에서 어떻게 다룰지 설정합니다.
제공되는 페널티 설정
모임에서 조정할 수 있도록 제공된 페널티 항목을 설정합니다.
피하고 싶은 시간대
모임에서 피하고 싶은 시간 범위를 지정합니다.
추천 후보 수
확인할 후보 일정의 개수를 설정합니다.

기본 점수 계산 규칙은 정해져 있습니다. 사용자는 모임별 제약과 제공되는 페널티를 조정하며, 모든 평가 기준의 가중치를 임의로 바꾸는 방식은 아닙니다.

핵심 알고리즘은 규칙·점수 기반입니다. Gemini는 추천 설명에 선택적으로 활용되며, 후보 일정을 결정하는 핵심 알고리즘이 아닙니다.

07 / Problem Solving

문제 해결 사례

모임마다 다른 추천 조건 설계

문제
고정된 추천 기준으로는 모임별 참석 조건과 선호를 담기 어려웠습니다.
행동
최소 인원, 필수 참석자 모드, 참석 불가 시간 처리, 페널티, 회피 시간대와 후보 수를 모임별 설정으로 구성했습니다.
배움
기본 점수 규칙과 사용자가 조정할 제약을 구분해 설계하는 일이 중요함을 배웠습니다.

여러 사용자의 일정 시나리오 검증

문제
참석자마다 일정과 권한이 달라 단일 계정으로는 다양한 조건을 확인하기 어려웠습니다.
행동
데모 계정 4개로 여러 일정 시나리오를 확인하고, 자동화 백엔드 테스트는 별도로 수행했습니다.
배움
다중 사용자 시나리오 확인과 자동화 테스트의 역할을 나누고, 실제로 확인한 범위를 구분해 기록해야 함을 배웠습니다.

복잡한 모임 생성 과정 나누기

문제
모임 생성에 필요한 설정이 많아 한 화면에서 입력과 수정을 다루기 복잡했습니다.
행동
12단계 카드형 위저드에 진행 표시, 이전·다음 이동, 최종 검토와 단계 수정을 구성했습니다.
배움
설정을 단계로 나누는 것과 함께, 전체 진행 상황과 수정 경로를 제공하는 일이 중요함을 배웠습니다.
